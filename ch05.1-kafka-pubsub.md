Think of Kafka as a distributed, durable event log.

An application writes events such as:

```text
OrderCreated { order_id: 123, customer_id: 7 }
PaymentReceived { order_id: 123, amount: 50 }
```

Other applications read those events and process them.

A simple Kafka flow looks like this:

```text
Producer → Kafka cluster → Consumer
              |
        stores events
        for later replay
```

## 1. Broker

A broker is a Kafka server.

If you run Kafka on three machines:

```text
Broker 1
Broker 2
Broker 3
```

Together, they form a Kafka cluster.

Brokers do three main things:

- receive events from producers
- store events on disk
- serve events to consumers

In GCP Pub/Sub, Google manages the equivalent servers for you. You do not normally see or manage individual brokers.

| Kafka | Pub/Sub |
|---|---|
| Broker | Google-managed Pub/Sub infrastructure |
| You choose broker count and placement | Google operates the infrastructure |
| You manage capacity and failures, unless using managed Kafka | Google handles scaling and availability |

## 2. Topic

A topic is a named stream of events.

For example:

```text
orders
payments
user-events
```

A producer writes an event to a topic, and consumers read from that topic.

The closest Pub/Sub equivalent is also a topic.

```text
Kafka topic:       orders
Pub/Sub topic:     orders
```

But Kafka topics are divided into partitions, which is a major Kafka concept.

## 3. Partition

A partition is an ordered append-only log inside a topic.

Suppose the `orders` topic has three partitions:

```text
orders
├── partition 0: event 0, event 1, event 2, event 3
├── partition 1: event 0, event 1, event 2
└── partition 2: event 0, event 1, event 2, event 3, event 4
```

Each partition is an independent sequence of events.

Partitions provide:

- parallelism
- scalability
- ordering within that partition

Kafka guarantees ordering inside one partition, not across the entire topic. The same event key is normally routed to the same partition, so events for the same entity can stay ordered. Kafka’s documentation describes this key-to-partition behavior and partition-level ordering explicitly. [Apache Kafka introduction](https://kafka.apache.org/intro/)

For example, if the key is `order_id`:

```text
order 123 → partition 1
order 456 → partition 2
order 789 → partition 0
```

All events for order `123` go to the same partition and are read in order.

### Pub/Sub equivalent

The closest Pub/Sub concept is an ordering key.

For example:

```text
ordering key = order-123
```

If message ordering is enabled, messages with the same ordering key can be delivered in order. However, Pub/Sub does not expose Kafka-style partitions to you. Pub/Sub manages the underlying distribution internally. [Pub/Sub ordering documentation](https://cloud.google.com/pubsub/docs/ordering)

A rough mapping is:

| Kafka | Pub/Sub |
|---|---|
| Partition | Internal service sharding, not directly exposed |
| Record key | Ordering key |
| Ordering within a partition | Ordering for messages with the same ordering key |

They are conceptually related, but not identical.

## 4. Replica

A replica is another copy of a partition stored on another broker.

Suppose partition 0 has a replication factor of 3:

```text
Partition 0

Broker 1: copy
Broker 2: copy
Broker 3: copy
```

There are three copies of the partition’s data.

This protects against broker failure. If Broker 1 dies, Kafka can use a copy on Broker 2 or Broker 3.

Important: Kafka replicates partitions, not necessarily an entire topic as one indivisible object.

For example:

```text
orders partition 0 → Broker 1, Broker 2, Broker 3
orders partition 1 → Broker 2, Broker 3, Broker 1
orders partition 2 → Broker 3, Broker 1, Broker 2
```

This spreads both data and workload across brokers.

The Kafka documentation describes replication as multiple brokers holding copies of topic partitions, with a common production replication factor of three. [Apache Kafka introduction](https://kafka.apache.org/intro/)

Pub/Sub also stores data redundantly, but Google does not expose “replica 1,” “replica 2,” or “replica 3” as concepts you configure for an ordinary topic. Replication is managed by Google.

## 5. Leader

Each Kafka partition has one leader.

For example:

```text
Partition 0:
  Leader:  Broker 1
  Follower: Broker 2
  Follower: Broker 3
```

The leader handles reads and writes for that partition.

A producer does not normally write independently to all three brokers. It sends the event to the partition leader:

```text
Producer → Broker 1, the leader
```

The leader then replicates the event to the followers.

The important point is that leadership belongs to a partition, not to the whole topic.

A topic with ten partitions may have:

```text
Partition 0 leader → Broker 1
Partition 1 leader → Broker 3
Partition 2 leader → Broker 2
...
```

This spreads the workload.

If the leader fails, Kafka elects an eligible follower as the new leader:

```text
Before:
  Broker 1 = leader
  Broker 2 = follower
  Broker 3 = follower

After Broker 1 fails:
  Broker 2 = new leader
  Broker 3 = follower
```

Pub/Sub has an internal equivalent of leaders, but it is hidden from you. You publish to the Pub/Sub service rather than to a particular server.

## 6. Follower

A follower is a replica that copies data from the partition leader.

```text
Producer
   |
   v
Leader
  / \
 v   v
Follower 1
Follower 2
```

Followers usually do not accept ordinary writes directly. They replicate what the leader has accepted.

If a follower falls behind, **Kafka may remove it from the in-sync replica set.** 

## 7. ISR: In-Sync Replicas

ISR means “in-sync replicas.”

These are replicas that are sufficiently caught up with the leader.

Example:

```text
Configured replicas: Broker 1, Broker 2, Broker 3
Currently in sync:  Broker 1, Broker 2
Broker 3:           too far behind
```

The ISR is:

```text
{Broker 1, Broker 2}
```

This relates directly to your original line:

```text
acks=all + min.insync.replicas=2
```

It means:

- the producer waits for the in-sync replicas to store the event
- Kafka requires at least two in-sync replicas
- if fewer than two are available, Kafka rejects the write

With replication factor 3:

```text
3 copies configured
2 copies currently healthy
→ writes can succeed

1 copy currently healthy
→ writes are rejected
```

This is why the setting prioritizes durability over availability.

Pub/Sub has similar durability goals, but you do not manually configure ISR or minimum in-sync replicas.

## 8. Producer

A producer is an application that writes events to Kafka.

Example:

```text
Order service → produces OrderCreated events
Payment service → produces PaymentReceived events
```

A producer chooses:

- topic
- optional key
- event value
- delivery settings such as `acks`

In Pub/Sub, a publisher is the equivalent of a Kafka producer.

| Kafka | Pub/Sub |
|---|---|
| Producer | Publisher |
| Produce record | Publish message |
| Topic | Topic |
| Record key | Ordering key, approximately |

## 9. Consumer

A consumer is an application that reads events from Kafka.

Example:

```text
Kafka → Fraud detection service
Kafka → Analytics service
Kafka → Email service
```

Consumers usually read events in order within each partition.

In Pub/Sub, a subscriber is the equivalent of a Kafka consumer.

However, the acknowledgement model differs:

### Kafka

A consumer processes an event and commits its offset:

```text
“I have successfully processed through offset 105.”
```

If necessary, it can move backward and replay older events.

### Pub/Sub

A subscriber receives a message and sends an acknowledgement:

```text
“I successfully processed this message.”
```

If the acknowledgement deadline expires or the message is negatively acknowledged, Pub/Sub can deliver it again. Pub/Sub is at-least-once by default. [Pub/Sub subscription overview](https://cloud.google.com/pubsub/docs/subscription-overview)

## 10. Offset

An offset is the position of an event inside a Kafka partition.

```text
Partition 0:
offset 0 → event A
offset 1 → event B
offset 2 → event C
offset 3 → event D
```

A consumer remembers its position:

```text
“I have processed through offset 2.”
```

If it crashes, it can resume at offset 3.

This is one of Kafka’s most important properties: reading a message does not immediately delete it. Kafka retains events according to its retention policy, so consumers can replay them.

Pub/Sub has no direct user-facing equivalent to Kafka’s numeric partition offset. Pub/Sub provides message retention and seek/replay features, but consumers generally work through acknowledgements and subscription state rather than manually tracking partition offsets.

## 11. Consumer group

A consumer group is a set of Kafka consumers cooperating to process a topic.

Suppose a topic has four partitions:

```text
Topic: orders
  P0  P1  P2  P3
```

And a consumer group has two instances:

```text
Consumer A → P0, P1
Consumer B → P2, P3
```

Each partition is assigned to only one consumer within that group at a time.

This gives load balancing and parallel processing.

If you add another consumer:

```text
Consumer A → P0
Consumer B → P1
Consumer C → P2
Consumer D → P3
```

But if you have more consumers than partitions, some consumers sit idle:

```text
4 partitions + 6 consumers
→ only 4 consumers can actively process partitions
```

### Pub/Sub equivalent

A Pub/Sub subscription is roughly equivalent to a Kafka consumer group.

Example:

```text
Pub/Sub topic: orders
├── Subscription: fraud-service
├── Subscription: analytics-service
└── Subscription: email-service
```

Each subscription receives its own logical copy of the topic’s messages.

Within one subscription, multiple subscriber instances share the work:

```text
fraud-service subscription
├── subscriber instance A
└── subscriber instance B
```

This is similar to multiple consumers in one Kafka consumer group.

The difference is:

- Kafka: you create consumer groups when consumers connect
- Pub/Sub: you explicitly create named subscriptions

## 12. Fan-out: one event, many systems

Suppose an order event should be processed by fraud detection and analytics.

### Kafka

Use two consumer groups:

```text
orders topic
├── fraud-service consumer group
└── analytics-service consumer group
```

Each group receives all relevant events independently.

### Pub/Sub

Use two subscriptions:

```text
orders topic
├── fraud-subscription
└── analytics-subscription
```

Each subscription receives its own delivery stream.

This is one of the closest Kafka/Pub/Sub mappings:

| Requirement | Kafka | Pub/Sub |
|---|---|---|
| One processing application with multiple instances | Consumer group | One subscription with multiple subscribers |
| Multiple independent applications | Multiple consumer groups | Multiple subscriptions on one topic |

## 13. Retention and replay

Kafka is naturally designed as a replayable log.

An event can remain available even after a consumer has read it:

```text
Producer writes event
Consumer reads event
Event remains until retention expires
Consumer can rewind and read it again
```

This is useful when:

- a bug corrupted downstream data
- a new service needs historical events
- a consumer was offline
- you need to rebuild a materialized view

Pub/Sub also supports message retention and replay/seek mechanisms, but its basic mental model is delivery plus acknowledgement. By default, Pub/Sub retains unacknowledged messages until they expire; acknowledged-message retention can also be configured. [Pub/Sub basics](https://cloud.google.com/pubsub/docs/pubsub-basics)

## 14. Delivery guarantees

Both systems require careful handling of duplicates.

### Kafka default mindset

Kafka consumers commonly operate with at-least-once processing:

```text
read event
process event
commit offset
```

If the application crashes after processing but before committing the offset, the event may be processed again.

Therefore, consumers should be idempotent.

For example, instead of blindly inserting:

```sql
INSERT INTO payments ...
```

use an event ID or business key to prevent duplicate effects.

### Pub/Sub default

Pub/Sub also provides at-least-once delivery by default. A message may be delivered again if it is not acknowledged in time or if acknowledgement handling encounters problems. [Pub/Sub best practices](https://cloud.google.com/pubsub/docs/subscribe-best-practices)

Pub/Sub supports exactly-once delivery for pull subscriptions, but it has specific constraints and does not eliminate duplicate business events caused by a publisher publishing the same logical event multiple times. [Pub/Sub exactly-once delivery](https://cloud.google.com/pubsub/docs/exactly-once-delivery)

“Exactly once delivery” also does not automatically mean “exactly once business effect.” For example, your service could charge a credit card and then crash before recording that it charged the card.

## 15. Kafka versus Pub/Sub: the mental model

The easiest comparison is:

```text
Kafka = a distributed, partitioned, replayable log that you operate or provision

Pub/Sub = a fully managed messaging service where Google hides the storage distribution
```

Kafka exposes more infrastructure concepts:

- brokers
- partitions
- leaders
- followers
- replicas
- ISR
- offsets
- consumer groups

Pub/Sub exposes more service-level concepts:

- topics
- subscriptions
- publishers
- subscribers
- acknowledgements
- acknowledgement deadlines
- ordering keys
- retention
- dead-letter topics

## 16. One complete example

Imagine an order platform.

### Kafka design

```text
Order API
   |
   | produces OrderCreated
   v
Kafka topic: orders
   |
   ├── partition 0
   ├── partition 1
   └── partition 2
          |
          | replicated across brokers
          v
Kafka brokers
   |
   ├── fraud consumer group
   ├── warehouse consumer group
   └── analytics consumer group
```

If `order_id=123` is the key, all events for order 123 are routed to the same partition, preserving order for that order.

### Pub/Sub design

```text
Order API
   |
   | publishes OrderCreated
   v
Pub/Sub topic: orders
   |
   ├── fraud-subscription
   ├── warehouse-subscription
   └── analytics-subscription
          |
          └── subscriber instances
```

Set `order_id` as the ordering key if you require ordering for each order.

Google manages the underlying brokers, partitioning, replication, leader election, and storage. Your main operational concerns become:

- subscription backlog
- acknowledgement deadlines
- redelivery
- ordering keys
- retry policies
- dead-letter topics
- retention

## The short version

Remember these mappings:

| Kafka concept | Simple meaning | Pub/Sub equivalent |
|---|---|---|
| Broker | Kafka server | Hidden Google-managed infrastructure |
| Topic | Named stream of events | Topic |
| Partition | Ordered slice of a topic | Internal sharding; partly analogous to ordering keys |
| Replica | Copy of a partition | Google-managed redundancy |
| Leader | Broker handling reads/writes for one partition | Hidden service implementation |
| Follower | Replica copying the leader | Hidden service implementation |
| ISR | Healthy, caught-up replicas | No direct user-managed equivalent |
| Producer | Application writing events | Publisher |
| Consumer | Application reading events | Subscriber |
| Consumer group | Consumers sharing work | Subscription with multiple subscriber instances |
| Offset | Position in a partition | No direct equivalent |
| Commit offset | Record processing progress | Acknowledge message |
| Key | Decides partition placement | Ordering key, approximately |
| Retention | How long Kafka keeps events | Topic/subscription message retention |

The most important distinction is this:

> Kafka gives you a partitioned log and exposes much of the machinery. Pub/Sub gives you a managed messaging service and hides most of that machinery.
